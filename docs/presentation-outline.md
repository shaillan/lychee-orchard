## 第 1 页 · 封面

**主标题**：智慧果园管家 —— 从田间到餐桌
**副标题**：电子档案 · AI 识别 · 一物一码 · 数据看板
**角标**：微信小程序 + H5 + Web 看板 ｜ FastAPI + SQLite（零外部依赖）

> 口播：我们做的不是又一个农事记录 App，而是把「种得好」变成「卖得贵」的那条链路。

## 第 2 页 · 痛点：果园的三个断点

| 断点 | 现状 | 后果 |
|---|---|---|
| 记录断 | 农事靠纸笔、微信语音，事后补不全 | 卖果时拿不出用药台账 |
| 判断断 | 病虫害靠经验，用药靠熟人推荐 | 超范围用药、间隔期没算清 |
| 信任断 | 收购商不信「没打药」，消费者不信「哪来的」 | 好果卖不出好价 |

**一句话结论**：果园缺的不是传感器，是**可核验的记录**。
**我们的解法**：让每一次识别、每一次用药、每一批采收，都自动留下一条能对账的记录。

## 第 4 页 · 落地全流程：从问题发现到持续运营

> 这一页回答「方案完整不完整」：不是做了个能跑的原型，而是把**调研 → 定义 → 开发 → 试点 → 培训 → 运营**六个阶段排成了一条链，每一段都有产出物和验收标准。

| 阶段 | 关键动作 | 产出物 | 谁来做 | 验收标准（怎么算这一步完成） |
|---|---|---|---|---|
| ① 问题发现 | 走访果农与镇农技员，翻现有纸笔台账，记录断在哪一步 | 访谈纪要、痛点排序 | 团队 | ≥3 户果农 + 1 位农技员，痛点排序能对上 |
| ② 需求定义 | 把痛点收敛成 4 个通关点，同时写清「不做什么」 | 需求清单（含排除项） | 团队 + 合作社 | 每条需求都能对应一个可演示功能 |
| ③ 原型开发 | 小程序 + H5 + 看板 + 规则库；先保证演示零风险，再谈扩展 | 可运行原型、153 个测试、104 张评测集 | 团队 | 一条命令启动，四步闭环完整走通 |
| ④ 小范围试点 | 1 个合作社、3 个地块，连续 4 周真实拍照与真实记账 | 试点记录、误判样本 | 团队 + 合作社 | 记录不断档；每周回收一批纠错样本 |
| ⑤ 培训与部署 | 田间 1 小时培训 + 纸质速查卡；村级服务站代管账号 | 操作手册、培训记录 | 合作社 + 镇农技站 | 果农能独立走完「拍照 → 处置 → 登记」 |
| ⑥ 运营与迭代 | 看板周报；纠错样本补进评测集；季度更新知识库与药剂表 | 周报、版本记录 | 镇农技站/合作社 + 团队 | 每月一次迭代，误判与漏记都可追踪 |

**当前进度（如实标注，不夸大）**

- ① 进行中：四个通关点已经定下来，但**原始访谈记录待补齐**——这是评委最可能追问的地方，不编数字；
- ② 基本完成：需求清单和「不做什么」已落到 4 个通关点，待 ① 的访谈佐证；
- ③ 已完成：代码、153 个自动化测试、104 张评测报告都在仓库里，现场可复现；
- ④⑤⑥ 已排期：给出的是验收标准，不是口号。

**两条闭环，一条在产品里，一条在项目里**

```
产品内：识别 → 处置 → 台账 → 放行/溯源        （第 6–8 页展开）
项目内：试点样本 → 纠错回流 → 评测集 → 提示词/知识库 → 新版本
```

**和后面几页的关系**：第 5–11 页是 ③ 原型开发的展开，第 12 页是 ③ 的现场验证；④–⑥ 讲的是这套东西走出演示环境之后怎么运转。

**为什么后三步能落地**：不新建系统、不改合作社现有记账习惯；单机部署，一个 U 盘就能搬到下一个果园；岗位上已有合作社管理员和镇农技员，不需要新设团队。

> 口播：我们不是把六步都做完来交差，而是把每一步的**验收标准**先定清楚——这样评委能判断我们到底能走到哪一步。

## 第 5 页 · 电子档案：果园的「底账」

**界面**：我的果园 → 分区示意图 → 点地块就地展开 → 完整档案

**讲三件事**：
1. **地块即档案单元**：编码 / 品种 / 面积 / 株数 / 定植年份 / 位置
2. **记录即流水**：农事记录、用药台账、产量趋势逐年沉淀
3. **状态即结论**：每块地实时显示「可采收 / 还需 N 天」，来自最后一条用药记录的安全间隔期

**Demo 提示**：点 A 区，卡片下方直接展开农事与用药记录，无需跳页。
**口播**：果农不需要理解数据库，他只需要点一下自己那块地。

## 第 6 页 · 拍照识别：AI 只做一件事

**流程条**：拍照 → 压缩上传 → 视觉大模型 → 归一化到 21 个类别 → **规则库**出建议

**核心主张（重点讲）**：
> **AI 负责「看到什么」，规则库负责「该怎么办」。**
> 大模型不直出用药建议。

**四道防误报闸门**（这是评委最关心的可靠性）：

| 闸门 | 做法 |
|---|---|
| 证据先行 | 先写看到什么病斑，写不出可辨识病征 → 降级「无法判断」 |
| 噪声排除 | 水珠、反光、果皮天然龟裂、未转色斑块不算病斑 |
| 置信度门槛 | < 65% 只展示、不给处置建议，提示人工复核 |
| 二次确认 | 带症状/危害部位/易混淆类别再问一次，答「没有该症状」→ 严格降级 |

**降级链**：云端主模型 → 退避重试 → 备选模型 → 本地模拟（标注来源，演示不中断）

## 第 7 页 · 处置闭环：识别不是终点

**闭环图**：

```
识别结果
   │ 规则库给出「建议处置 + 理由」
   ├─ 按建议用药 ──→ 写用药台账 ──→ 回链识别记录 ──→ 待办销项
   ├─ 人工清除   ──→ 写农事记录 ──→ 同上
   ├─ 误判       ──→ 标记不处置
   └─ 忽略       ──→ 标记不处置
```

**安全间隔期联动**：输入「距采收 5 天」→ 长间隔期药剂自动过滤 → 若全部来不及，明确建议人工清除，而不是硬开药。

**闭环的验收方式**（对应第 4 页 ④ 试点）：每条识别记录都能回答三个问题——**处置了没有**（台账里有没有对应记录）、**处置对不对**（是否在推荐药剂与安全间隔期内）、**什么时候处置的**（时间戳 + 操作人）。试点期每周抽 10 条核对，漏记和错记都能列出来。

**口播**：很多方案止步于「识别准确率」，我们关注的是识别之后，果农到底做了没有、记了没有、能不能查。

## 第 8 页 · 一物一码：让每一批果可核验

**编码**：`LZ / P03 / 20260702 / 0001`（品种 / 地块 / 采收日期 / 包装序号）

**三层可信**：
1. **放行可信**：建批次时校验该地块全部用药记录，间隔期未到 → 状态 `blocked`，**不生成销售溯源码**
2. **过程可信**：种植 → 管护 → 销售三段式，扫码即见农事、用药、检测、流向
3. **防篡改可信**：关键节点写入哈希链，`SHA-256(原文 + 上一条哈希)`，改任一条即断链并定位到记录 ID

**现场可演示**：# 链校验通过 ✅ → 改一条存证 → 刷新 → ❌ 第 N 条被篡改 → 一键还原

**落地产物**：批次质量合格证（A4 单页，带二维码、间隔期状态、链校验结果、签字栏）；拦截批次印红「已拦截 · 不得销售」

**诚实边界（主动说明，加分）**：单机哈希链只能证明「写入后未被改」，不能证明「录入时为真」；更强证明需把链头对外锚定。

## 第 10 页 · 加分能力

- **天气联动**：Open-Meteo 未来 3 天降雨/湿度 → 霜疫霉病风险 → 自动生成「雨前预防」待办；地区可在界面设置，H5 与小程序共用
- **采前双预警**：品种日历给出「最佳采收窗口 / 物候期」；久旱转雨 + 品种敏感度命中时提示裂果风险（糯米糍阈值最低）
- **采后 72 小时**：批次记录离树 → 预冷 → 发运 → 到货，离树超 24 小时未预冷直接进 critical 待办
- **农残快检**：拍照上传报告 + 人工录入结论；「不合格」自动把批次改为拦截，检测节点写入哈希链
- **巡园报告**：一次最多 9 张照片，串行识别后聚合出异常计数、重点地块与监测建议
- **语音填报**：微信同声传译插件，备注说一句自动转文字；无插件环境自动隐藏并降级手动输入
- **病虫害知识库**：18 种病虫害全字段（症状 / 高发期 / 监测要点 / 易混淆鉴别 / 非化学 / 生物防治 / 推荐药剂），支持全文搜索、病害筛选与「本月高发」提醒；断网可读本地缓存
- **识别纠错回流**：误判时可选填真实类别，样本可直接导出（模型判为 X → 实际为 Y），用于补评测集与后续微调；看板展示纠错率
- **台账留痕**：农事 / 用药记录不可改删，录错只能作废并留原因与操作人；作废记录退出放行与合规统计，但永久可查
- **识别评测**：`tools/prelabel.py` 模型预标注 + 人工改错，`tools/eval_vision.py` 输出准确率 / 分类召回 / 混淆矩阵 / 拒答率 / 非目标误报
- **适老化**：大字模式一键切换并持久化，全页面生效
- **待办驱动**：5 类待办自动汇总（间隔期 / 农事空档 / 批次拦截 / 未处置识别 / 天气），每条都能一键跳到处置入口
- **响应优化**：天气缓存 stale-while-revalidate + 启动预热，待办接口从 1.5s 降到 70ms

## 第 11 页 · 技术架构与可信度

| 层 | 选型 | 理由 |

**设计原则**：能砍则砍——不引入 MySQL、Redis、消息队列、区块链。

## 第 13 页 · 价值与展望

**已实现的价值**
- 对果农：拍一张照就知道怎么处置，不用记法规
- 对合作社：每批果都有可导出的合规证据
- 对镇农技站：用药合规明细一键导出，日常抽查有据可查
- 对收购商 / 消费者：扫码即见全过程，链可校验

**下一步（按投入产出排序）**
1. **落地试点**：1 个合作社、3 个地块、连续 4 周，验收标准见第 4 页 ④
2. 与收购商质检单打通，溯源页直接出示农残报告
3. 多果园 / 多角色权限，从单机原型走向合作社部署
4. 扩充评测集，用纠错回流样本迭代提示词 / 小样本微调

**结束语**：让每一颗荔枝，都有一份说得清、查得到、改不动的档案。

## 附录 A · 常见提问与回答要点

| 提问 | 回答要点 |
|---|---|
| 你们的方案完整吗？走到哪一步了？ | 六个阶段都有验收标准（第 4 页）：调研、需求、原型、试点、培训、运营。如实说进度：原型已完成并有测试与评测报告，试点和培训已排期；不把计划说成已完成 |
| 调研做了多少户？ | 只报真实数字和地点；没做完就说「目前访谈了 N 户，计划补充到 M 户」。评委追问时，编的数字一戳就破，如实说进度反而得分 |
| 试点能不能本地化？ | 单机部署，一个 U 盘可迁移；合作社管理员 + 镇农技员两个现成岗位，不需要新设团队；培训 1 小时 + 纸质速查卡 |
| AI 识别不准怎么办？ | 四道闸门 + 置信度门槛 + 人工复核；低置信度不自动给建议；无法判断时不建议用药；误判可选填真实类别并导出为评测 / 微调样本（自建评测集：准确率 / 拒答率 / 非目标误报） |
| 记录填错了能改吗？ | 不能改也不能删，只能作废并留原因与操作人；作废记录退出放行与合规统计但永久可查，形成可审计轨迹 |
| 为什么不让大模型直接开药？ | 超范围用药是法律风险；用药必须来自登记农药库与安全间隔期规则 |
| 哈希链能防造假吗？ | 只能证明写入后未被改；录入真实性要靠现场拍照、操作人、GPS 等，链头对外锚定才能更强 |
| 果园没网怎么办？ | 小程序可缓存最近数据；识别失败自动降级本地模拟；后续可做离线队列 |
| 成本多少？ | 后端单机可跑；识别默认用免费模型，按量付费可换；无数据库授权费用 |
| 数据从哪来？ | 内置 3 个地块、5 年产量、农事/用药/识别/4 个批次的演示种子数据，可一键建库 |
| 和现成农事 App 的区别？ | 别人做记录，我们把记录变成**放行依据**和**可核验的溯源码** |
| 能规模化吗？ | 接口与端解耦，SQLite 可换 PostgreSQL；识别走标准 OpenAI 兼容协议，随时换供应商 |
